# Implementation plan — commerce-integration

The master plan across all three repositories lives in [`commerce-platform/docs/implementation-plan.md`](https://github.com/sta-ko-je-reko-ja-sam-reko/commerce-platform/blob/main/docs/implementation-plan.md). This is the slice this repository owns.

## What this layer is for

It is the layer a group-level integration platform leaves behind when a business is carved out: the API façade, the event backbone, the canonical model, and the orchestration everything else quietly depended on.

Its defining constraint: **no Business Central table, field or enum name may escape it.** Mapping happens here so that domain services on the other side never learn the ERP's vocabulary.

## Phase 1 — the catalogue path

Three functions, in this order.

**Catalogue sync.** Pull the item delta with the keyset cursor, map to the canonical model, upsert into the platform projection, advance the watermark only on durable application. The cursor module is done; what is missing is the caller around it — the HTTP client, the mapping, and the write.

**Reconciliation.** Nightly. Pull content hashes cursor-paged, compare against the projection, repair differences, emit the correction count as a metric. A rising count is the early signal that the event path is broken.

**Outbox collector.** Poll the connector's change outbox, publish to the Service Bus topic, mark collected. This is what keeps the projection warm between delta pulls.

## Phase 2 — the read-through path

**Price and availability proxies.** Bulk only, capped at 100 lines, behind the circuit breaker, returning the provenance envelope. Chunk baskets larger than the cap and run the chunks concurrently against a bounded inflight limit.

**Credit proxy.** No cache. Fails closed — when it cannot be resolved, checkout blocks.

## Phase 3 — the write path

**Order gateway mapping.** One platform `POST /orders` fans into a connector staging header, its lines, and the idempotency key. A duplicate key fails on the connector's unique index; catch that and return the original result rather than surfacing a conflict.

## Phase 4 — the façade

API Management policies as code: partner keys, throttling, versioning. Deploy the Bicep. Wire the deployment pipeline with environment approval gates.

## Standing rules

- **Honour `Retry-After` over computed backoff**, including when it exceeds the local ceiling. The ceiling bounds our impatience, not an instruction from the service.
- **Never page with `gt` alone or `ge` alone.** Both fail silently. See [`docs/catalogue-paging.md`](catalogue-paging.md).
- **Every write carries an idempotency key** generated by the originating business action, stable across retries of that action.
- **No outbound HTTP inside a Business Central posting transaction.** The connector stages the intent; this layer ships it.
- **Degradation is labelled, never silent.** A fallback value must be distinguishable from a resolved one by the consumer.
